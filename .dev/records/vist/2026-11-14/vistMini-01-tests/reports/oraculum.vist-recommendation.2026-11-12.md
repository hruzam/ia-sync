## Answer to relay

VIST should make independent native sessions observable enough for bounded collaboration.
Its locked responsibility is observations; deciding what to request and delivering that
request belong to separate components. The intended cooperation is: scoped work in a file,
a short notification to the intended seat, that seat reads and returns a correlated result,
and the owning head verifies it. Telemetry helps decide when to notify and when to involve
the human; it cannot establish acceptance, completion or authority.

The current trial has a useful but incomplete result: three consumed Codex→Claude messages,
zero qualifying reverse messages. The next experiment should establish one Claude→Codex
native delivery into the actual bound receiving session, with a small useful file-based
answer and explicit correlation. Then finish the three-each-direction and refusal/recovery
matrix. Qualify passive VIST observations separately against witnessed events. Office's
native success is a candidate-carrier precedent, not proof of home's backend ownership or
of Claude's access to that route.

## Intended flow and source authority

**Locked:** nablarva `.dev/session/flag.md:235` (L20) defines VIST as a shared observation
principle and intended protocol. Antensor is a candidate implementation and the envelope
is proposed. Observations authorize nothing. L21 requires a separate release for transport
implementation, activation, delivery or adoption. `docs/ARCHITECTURE.md:144` preserves this
split; its delivery section at line 200 keeps carrier alternatives open.

**Design intent:** `.dev/session/nablarva-X4-vist/raw/vist-01-principle-and-applications.md`,
especially lines 58–110 and 216–238, supplies this cooperation cycle:

1. A seat completes bounded work and leaves the request/result in the agreed file plane.
2. Passive observations report session evidence: expected occupant, idle, busy, approval,
   input needed, error or unknown. They retain provenance and uncertainty.
3. A controller combines that evidence with the authorized task and chooses an action.
4. A separately authorized actuator delivers a short pointer and records its own outcome.
5. The recipient reads the file under its own rules, accepts or refuses scope, and supplies
   the owed correlated return. The head checks the artifact and records the verdict.
6. The exchange ends by rule; uncertainty or a permission need returns to the human.

Controller/actuator details remain proposed. Sender identity, recipient identity, task
correlation and runtime thread identity must remain distinguishable. Vendor adapters may
differ without changing the meaning of the handoff. Same-host evidence does not establish
cross-host behavior; vistMini's RUNBOOK explicitly leaves cross-host runs to another session.

The HELLO r0 proposal (`raw/hello-01-contract.md:15–35,259–272`) illustrates send, read,
reply once, stop. Its vendor-free route constraint belongs to that experiment; it neither
adopts keystroke delivery animal-wide nor prohibits native candidates in today's ia-sync
trial. The retained X4 tree has no root RUNBOOK/STATUS or live pulse row. Its raw files are
design/evidence sources, not a currently authorized execution plan.

## What this trial must prove

The existing `vistMini-01-tests/RUNBOOK.md` remains the acceptance contract, owned by
Trajectory. It requires three ordinary messages delivered **and consumed in each direction
without operator relay**, the pre-registered refusal/recovery cases, each runtime's permission
boundary, stated limits for VIST, independent verification and Majkee's acceptance.

Distinguish file availability → notification attempt → submission into the intended session
→ consumption → verified work. A successful send call proves only its own step. An explicit
consumer stamp or correlated worked return proves consumption; idle/busy changes do not.
This distinction is already in `protocol-proposal.md` and `HANDSHAKE.md:28–39`.

Check the semantic cases as well as adapter cases: expiry, wrong recipient/path, duplicate
work, retry/hop limits and recovery after uncertain submission. The C01–C18 stand-in matrix
explicitly defers several of these. Passing stand-ins does not establish live TUI behavior.
Require preserved drafts, correct recipient/lifetime binding, no shell execution of a
pointer, no blind retry, and a bounded end to the exchange. State any permission condition
that was not tested; auto mode did not establish the intended allowlist/denial pair.

**Observed in checked local records:** cycle03 VERDICT confirms Codex→Claude 3/3 and
Claude→Codex 0/3. t01/t02 cleanly refused; t03 was uncertain after text entry and Majkee
supplied Enter. Preserve t03's attempt key; it is not a delivery success to retry. Fixture

**Historical evidence:** X4 `raw/hello-world/FINDING.md:7–13` records a successful

received payload or transfer the sender's permissions.

## Recommended experiment, for Trajectory to issue

**First: one reverse-direction delivery and useful return.** This is a proposed next POINT,
not an assignment issued by this note.

- Preflight the exact existing Codex target on home: current thread identity, visible native
  session, owning route, readiness and permitted external sender. Use local capability/help
  evidence to select a route. `codex queue` is a candidate from cycle04 research, not a proven
  live door. A fresh app-server or `exec resume` must not be assumed to join the existing TUI.
- Trajectory writes one fresh bounded request with a unique message ID, nonce, recipient,
  reply path and stop condition. A useful tiny task is to read the two cited VIST/gate sources
  and return the observation/authority distinction plus the unmet trial criterion.
- From Trajectory's own Claude execution context, submit one pointer through the selected
  authorized route. Record submission result and receiver evidence; require the bound
  Codex session to identify the message and produce the correlated file answer. Use the
  already-qualified outbound adapter only if its current checks pass to notify Trajectory
  of that return. Trajectory reads and verifies it. No acknowledgement loop follows.
- Success means the right existing session consumed the scoped request, returned correct
  content with correlation, and no operator completed submission. A read-only TUI/log
  observation may witness identity; a send exit code cannot substitute for it.
- On writer conflict, ambiguity or uncertain delivery, preserve the attempt and stop. Do
  not remove locks, force ownership, start a substitute session or retry through another
  carrier. Report the blocked direction. Backend ownership becomes a focused diagnostic
  question only as far as needed to establish the intended receiver.

**Then:** repeat to the existing gate's count and finish the semantic refusal/recovery
coverage; disruptive cases remain isolated as the RUNBOOK requires. Three successes are a
smoke trial, not reliability statistics. A Codex→Codex handoff of this note cannot count
toward Claude→Codex.

**After carrier evidence:** propose a separate passive observation qualification. Compare
recorded screens/events with independently witnessed session states and explicit receipts,
including busy, ready, approval and unknown. Keep controller decisions in shadow mode and
label self-caused echoes. Measure false-ready classifications and uncertainty instead of
inferring them from successful delivery. No new watcher, actuator or global configuration is
released by this recommendation. Exact observation states and schema still require their
own contract and qualification under L20.
