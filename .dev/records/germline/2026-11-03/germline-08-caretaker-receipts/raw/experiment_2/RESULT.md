## What changed and what was proved

The deploy-inert receipt runner creates an exclusive pending operation record before
invocation. Completion atomically replaces that record with exit/timing, output hashes and
selected state identity. Inspection distinguishes validated completion, a living pending
runner, and unknown outcomes. An existing operation record always refuses re-execution.

Ten local checks pass, including lost caller return, live/dead pending, altered output,
nonzero exit, malformed syntax/structure, nonobject state and duplicate refusal. Parent
added malformed-structure handling after reviewing the caretaker's original eight checks;
the initial RETURN is preserved beside the qualified VERDICT.

In the live trial, the driver intentionally ignored peer A's returned runner stdout, then
used a separate receipt inspection to recover validated completion. The captured task result
remained intact. This is a caller-response simulation, not an induced transport failure.
Both peers' open/ask/resume operations are independently hash-validated; neither task was resent.

## Recommendation and limits

Keep the existing transport and this receipt-first wrapper experimental. Explicit low effort
is suitable for the two bounded source checks just witnessed; this does not qualify it for
unrestricted investigation or recovery decisions. Retain fixed prompts/read budgets for a
later real guide-to-program audit; send the main only verified findings and genuine decisions.

No live first-turn fault, compaction, collision, destructive recovery or restart persistence
was tested. The transport's first-turn ID-persistence gap remains unfixed. A dead runner or
null vault cannot establish remote absence and never authorizes an automatic resend. Atomic
local receipts are not a remote exactly-once guarantee or a power-loss durability proof.

No Claude process/SDK, new authentication, source/global primitive change, deployment, commit
or push occurred. G07 evidence, G03 review boundaries and unrelated edits are preserved.
