# 1. Problem

Current BUS models one bounded exchange very well:

    POINT -> RETURN -> VERDICT

But majkee is using multi-session runs where one persistent head
(cSharp) coordinates several parallel worker sessions.

Example:

                       cSharp
                         |
              +----------+----------+
              |                     |
         Atlas[coder-A]         Atlas[coder-B]
              |                     |
              +----------+----------+
                         |
                       cSharp

Both workers may receive work from the same logical moment and return
independently.

The missing concept appears to be:

    WHICH exchanges belong to the same coordination turn?

This matters especially because the human may physically relay prompts
between CLI sessions. The human and every agent need to know whether a
message belongs to turn 03, turn 04, etc.


# 2. cSharp model

cSharp is first-in / last-out.

It:

- authors/owns the opening session shape;
- remains navigator and status_owner;
- delegates bodies of work;
- receives worker returns;
- verifies or arranges crossed verification;
- decides what findings affect the next coordination turn;
- closes the gate if possible.

This should remain RUNBOOK law, not a vendor-specific skill.

Skills/slash commands are instruments beneath the RUNBOOK discipline,
not competing authorities.


# 3. Stable callsigns

A multi-seat RUNBOOK should establish unambiguous seat identities for
the lifetime of the session.

Example:

    csharp          = Atlas[cSharp]
    coder-a         = Atlas[programmer-A]
    coder-b         = Atlas[programmer-B]
    verifier        = Cartan[assay]

The exact syntax is open.

Important property:

    one live seat -> one stable callsign/slug

Two incarnations of the same named agent must not become ambiguous.

The callsign belongs to the RUNBOOK roster because identity is fixed
at session authoring.

BUS receipts then use that identity.


# 4. Candidate TURN model

We are considering adding a coordination layer ABOVE individual BUS
cycles.

Conceptually:

                  TURN 03
                     |
             cSharp dispatch
             /             \
            /               \
       cycle 07           cycle 08
       coder-a            coder-b
          |                  |
       RETURN             RETURN
          |                  |
       VERDICT            VERDICT
            \              /
             \            /
              cSharp JOIN
                   |
             STATUS rewrite
                   |
                 TURN 04


TURN does NOT replace POINT / RETURN / VERDICT.

Individual exchanges remain independently inspectable.

TURN says:

    "these cycles were concurrently part of one cSharp
     coordination decision."


# 5. Important open design question

We have NOT decided whether TURN should become a new BUS artifact.

Current canon permits only:

    *.point.md
    *.return.md
    *.verdict.md

Therefore consider at least these alternatives.

## A — minimal / canon-preserving

Do not create a new BUS kind.

Add a `turn:` identifier inside POINT and VERDICT metadata.

Example:

    cycle: 07
    turn: 03
    from: csharp
    to: coder-a

and:

    cycle: 08
    turn: 03
    from: csharp
    to: coder-b

cSharp determines closure from the set of cycle VERDICTs and rewrites
STATUS.

No TURN file exists.


## B — first-class TURN receipt

Introduce a new cSharp-owned BUS artifact representing the coordination
join.

Possible conceptual shape:

    03.csharp.turn.md

or another naming scheme.

It would identify:

- participating cycles;
- expected seats;
- completed / blocked cycles;
- joined findings;
- unresolved curvature;
- decision that generates the next turn.

This requires amending current BUS law.


## C — another shape

If both A and B are wrong, propose the smallest cleaner mechanism.


# 6. What we explicitly do NOT want

We do not want:

- a chat transcript;
- an inbox disguised as BUS;
- mutable "latest message on top" agent cards;
- several agents editing one shared markdown table concurrently;
- BUS becoming STATUS;
- file existence interpreted as proof that an agent read something;
- worker recommendations automatically becoming current work;
- vendor-specific identity semantics becoming session law.


# 7. Human relay

The human may be the physical carrier between sessions.

Therefore a relay should be mechanically understandable as something
like:

    TURN 03
      cSharp -> coder-a
      cSharp -> coder-b

    returns arrive

      coder-a -> cSharp
      coder-b -> cSharp

    cSharp joins/verifies

    TURN 04

An unexpected finding may legitimately send the process backwards or
create a corrective cycle.

We should NOT falsify history by renumbering old turns.

Assess how this should be represented.


# 8. STATUS boundary

Our current assumption:

RUNBOOK = fixed contract / roster
BUS     = past exchanges
STATUS  = present position

TURN must not create another doing-state.

If TURN exists as an artifact, after it is written it should describe
a coordination event/receipt, not compete with STATUS.next.

Please attack this boundary carefully.

And I would **not yet choose A or B**. There is a real architectural question here.

Current canon already gives us two useful anchors: the cSharp collateral explicitly defines the head as “first in, last out,” navigator/status owner, with crossed witnesses rather than self-confirmed gates; and BUS deliberately says it is *past exchange*, not doing-state, inbox, or notification mechanism. 

My current lean is **A-plus**: `turn:` becomes a grouping coordinate on ordinary cycles, while a cSharp JOIN is probably a specialized VERDICT rather than a fourth BUS primitive. That preserves the unusually clean POINT/RETURN/VERDICT grammar. But I would specifically leave this unresolved for Symmetry—the strongest reason to involve her is to attack whether that “JOIN as VERDICT” is semantically honest or merely us forcing a new concept into an old noun.

Also, one correction to something I said in voice: **the existing BUS already has `<seat>` in its filename and defines it as the writer**. So we are not inventing seat identity for BUS. What we are proposing is strengthening the RUNBOOK roster so two Atlas incarnations have stable, unambiguous seat/callsign identities that BUS can reuse. That is a considerably smaller change.
