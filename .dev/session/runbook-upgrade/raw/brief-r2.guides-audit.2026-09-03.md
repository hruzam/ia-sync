# BRIEF R2 — audit an existing file plane, and price two prior-art deltas

## Standing rules from round one

Field practice over documentation ideals. Date your vendor facts. Separate
**documented fact** from **community practice** from **your own inference**, and
mark confidence. `#no-invented-attribution` — if you cannot place a source, say so.

Two additions for this round:

**Audit first; redesign is earned, not assumed.** The enclosed guides are in
daily use by a solo operator with agents on two machines. Judge what is there
before proposing anything else.

Redesign is welcome — including replacing a component outright, or the whole
set — but every proposal must be **anchored to a finding**: name the specific
defect in the enclosed material, then propose. A proposal that does not cite
what it fixes will be discarded unread, however good it is.

Proposing is cheaper and reads better than auditing, so state plainly when a
proposal is speculative rather than remedial. Both are wanted; only one is
allowed to disguise itself as the other.

**Say what is wrong before you say what is good.** A confirmation costs nothing
here. The operator's stated failure mode is confident analysis papering over thin
material, and this brief is one of two independent reads whose disagreements are
the product.

## PART A — the enclosed system, read cold

The enclosures are four STYLE+LAW guides describing a session file set, plus two
agent definitions of different vintage.

1. Read the four guides as a **fresh agent would**: you have the folder, you have
   the guides, you have no memory of the session. Can you resume work? Name
   precisely where you would stall.

2. Where do the four guides **contradict each other**? Quote both sides. Do not
   smooth a contradiction into a nuance.

3. Where does a guide state a law it cannot enforce — a rule that depends on the
   operator or the agent voluntarily complying, with nothing detecting a breach?
   List them. For each, say whether the honour system is adequate or is a latent
   failure.

4. **What is missing that the guides do not know is missing?** This is the
   question the operator most wants answered and the one least likely to be
   answered by comparing against a checklist.

5. Each file in the set claims a distinct job. Are those jobs actually disjoint,
   or do any two overlap enough that a writer would hesitate about where a line
   belongs? Test the boundaries with concrete example lines, not in principle.

6. The set has **no length bound** on any file except one implicit reading-time
   standard. Given what current evidence does and does not support about
   instruction-file length, what bound — if any — should these files carry, and
   should it be expressed in lines, words, reading time, field count, or not at
   all?

7. What in this set would you expect to be **abandoned within six months**, and
   why? Answer even if the answer is "nothing."

8. The two enclosed agent definitions are roughly four months apart in vintage.
   What did the later one learn? What did it lose?

9. Assume the operator will hand this set to a second person. What breaks first?

10. Rank the whole set against current field practice: what here is **ahead**,
    what is **at par**, and what is **behind** and should simply be replaced by a
    shipped feature?

## PART B — pricing a prior-art delta

Two components exist as working local designs. Both now have plausible vendor or
community coverage. The question in each case is not "does prior art exist" — it
does — but **what residual delta survives**, and whether that delta is worth
maintaining.

Answer each in the shape: *what the existing thing covers · what it does not ·
what it costs to adopt · what the local design should keep, if anything.*

11. **Cross-vendor consultation.** A local protocol lets agents under one vendor
    consult agents under another: a bounded assignment, a single reply, an
    independent verification step, all as files in a git-tracked directory, with
    exchanges capped at a few touches and no long-lived relay process.

    What do the official cross-vendor mechanisms now cover, concretely? What do
    they *not* cover — specifically around verification, provenance, ownership of
    the record, and what survives after the exchange ends? Is the file-based form
    redundant, complementary, or superseded?

12. **Competence escalation.** A local pattern has a mid-tier agent spawn a more
    senior agent when a decision exceeds its competence, chosen by the spawning
    agent.

    How does that compare with native advisor/escalation mechanisms now shipping?
    What does the native form gain, what does it constrain, and where is it not
    available? Is spawning-a-senior-agent still the right shape for anything?

13. For both: what should the operator watch for that would tell them the local
    design has become dead weight — a concrete observable, not a feeling?

## PART C — one design under load

14. An operator runs several projects concurrently and switches between them.
    Session-scoped state is deliberately pruned when work closes; the layer above
    the project holds standing operator preferences.

    **What actually fails at switch time?** Describe the observed failure modes
    from field reports — what people report losing, re-deriving, or getting wrong
    when they come back to a project after time away or after working elsewhere.

    Answer the failure modes first. Only then, if the evidence supports it, say
    what mitigates them and at what cost. If the honest answer is that the field
    has no good answer, say that.
