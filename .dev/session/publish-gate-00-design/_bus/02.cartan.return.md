# Fold check — the direction holds; four contracts still disagree

**Weakest assumption:** hashing an operation's entire destination set produces the exclusion
P5 requires. It distinguishes unequal sets, including sets that overlap and must exclude
each other. Moving that hash-keyed lock outside the common dir fixes location, not overlap.

**Verdict: REVISE, on the bounded corrections below.** P1 is faithfully folded; most of P2
and the r3 ownership direction survive. P3–P6 still contain execution-level contradictions.
Majkee's **every unpushed commit remains droppable** decision stands, including already
deployed commits. `pg-drop` and its future button stay. No new architecture or gavel is sought.

**Primary risk:** two permitted publications overlap at the live target despite both holding
their own mutex, or a valid selected prefix is refused because its OID is mistaken for HEAD.

**One alternative:** finish the existing small operation model: one coarse deployment mutex
for ia-sync's target on this host/user, shared target-state evidence, separate selected OID
and observed HEAD, and one unambiguous muticula-aware revert route. Avoid introducing a
general resource-lock service to repair these points.

## Required corrections

### R1 — Overlap needs one lock; shared target truth must survive another clone (P2/P5)

§3's manifest and §3b key the mutex by a digest of the sorted destination set. Consider a
full deploy writing `{zsh, codex, claude, …}` and a Codex-only deploy writing `{codex}`.
Their sets and digests differ; both locks succeed; both write the Codex destinations.
The same defect can occur between two full snapshots if the key enumerates actual files
and one snapshot adds/removes a file.

**Small fold:** one stable, coarse host/user ia-sync deployment-domain mutex, shared by all
clones, snapshots and full/partial/redeploy paths. This can intentionally serialize disjoint
legs. An overlap-aware set of locks is an alternative but unnecessary v0 complexity. Do not
derive the exclusion identity from the selected snapshot's exact file inventory.

There is a second half to the same contract. Receipts/stamps remain common-dir-local:
clone A reads its stamp for C; clone B deploys D under the shared mutex; A later acquires it
and still sees C in A's private stamp. Rechecking that stamp cannot detect B's deployment.
Keep operation history wherever appropriate, but put the current target generation/state
under the shared deployment domain, or explicitly obtain and validate equivalent live-target
evidence under that mutex. The old private receipt is history, not current target truth.
Q4 is therefore not entirely cosmetic when multiple clones are supported.

No claim or beacon authority is added. This is the same adapter transaction boundary P5
already requires; direct deploy.sh remains a declared cooperative bypass.

### R2 — Pin selected OID and observed HEAD separately (P6)

§4 line 278 defines `expected_head` as “the selected commit”; §4 then requires HEAD to equal
it. Example: the buffer is `c1 → c2 → c3`, HEAD is c3, and the operator selects c1.
The intended prefix publication is valid, but the new validation rejects it as stale.

**Fold:** `selected_oid=c1`, `expected_head=c3` captured at plan time. Revalidate HEAD against
the observed c3; deploy/push c1; calculate remaining commits from reachability, with c2/c3
remaining local. Mirror the distinction in the JSON example. Apply the same discipline to
drop's computed post-rewrite OID: a new result binding is not the old expected HEAD.

Also keep the observed remote tip separate from a merge-base. §1 currently offers either as
`observed_base`, while execute compares it with the remote tip. Give each value one meaning;
otherwise a legitimate diverged graph can fail an equality check for the wrong reason.

### R3 — One commit route, including the human alternative (P4)

The prepared revert is now `git revert --no-commit`, followed by `muticula commit`, which
carries the intended correction. But §7 lines 413–415 still offers “the human runs
`git revert` by hand” while saying the gate is honoured either way. Plain revert creates its
own commit. A human terminal does not route that commit through muticula.

**Fold:** specify the no-commit preparation plus gate in both paths, or remove the raw-revert
alternative. Keep claims/adoption and dirty-state checks explicit, and state how preparation
and abort are coordinated with other writers to the shared index. A clean-index observation
is not a transaction spanning preparation, conflicts and commit. An explicit operator
maintenance interval is a lean option; don't imply that the deploy mutex supplies it.

The three-state table must use muticula's current authority decision, not just equality with
`keys/<id>`. Include closed/reaped/stopped credentials, damaged/unreadable state and the pinned
host/checkout in refusal handling. Publish-gate must not maintain a second implementation of
muticula's grant logic. The closing sentence for pg-drop, saying ID presence decides the
commit route, also needs the table's **validated enrollment** condition.

Keep the explicit operator route, but say how it stays off agent routes under r3's deny-list
contract; an interactive confirmation by itself does not establish a human. Step-0's known
coverage limits apply here too. This is completion of P4, not a request for stronger human
authentication or new muticula resources.

### R4 — “Before the first merge” is not yet a unique publishable prefix (P3/P6)

The linear-range restriction is acceptable as a v0 scope limit, but the core algorithm is
still described through `rev-list --reverse`. In a graph `base → B` and `base → C`, later
merged as M, both B and C may appear before M in that list. They are siblings, not one
prefix chain. Separately, a merge-free local range can diverge from the current remote tip,
making a normal push impossible even though its commit list looks linear.

**Lean fold:** refuse v0 publish selection for a range containing a merge, and require the
observed remote tip to be an ancestor of the selected OID and the selection to belong to
the approved local history. Then verify the selected prefix's ancestry before any deploy.
If the head retains partial selection before a merge, define the chosen ancestry path
explicitly; commit-date order is not that definition. Do not deploy a candidate already
known to require a rejected non-fast-forward push.

This narrows publication support, not majkee's drop eligibility. Unsupported history can
require an explicit human plan. Integration advice must use §1a's resolved project policy:
the generic rejection text still literally says `git pull --rebase` (§7 line 528), which is
not nablarva's recovery command. Do not change nablarva's topology to suit this core.

## Small consistency fixes in the same fold

- Put receipt creation/`deploying` before deploy in the rendered plan, not only §2a prose.
  Carry drop's history-operation outcome in the concrete receipt alongside independent
  deploy and push results; the current field sketch mostly lists deploy states.
- Retain known earlier publication facts as P3 requested. A current fetched ref is evidence
  about that ref now; it must not erase a prior publication receipt when classifying drops.
- “Observed leftover” requires current filesystem presence, not merely an old receipt saying
  it once existed (§7 lines 468–469). Otherwise label it an expected/candidate residual.
  The JSON `orphans: revert/drop only` comment must include forward deletions too.
- Post-push exact equality is a conservative sufficient observation, not the only proof that
  a commit was published: another successful publisher may immediately advance to its
  descendant. Preserve the push receipt and distinguish published-but-advanced from unknown
  when ancestry can be verified. A mismatch may conservatively stop, but is not proof that
  publication failed or permission to rewrite the selected commit away.
- Make §1's receiving-host sentence point explicitly to §3a; keep dirty-tree manual deploys
  labelled noncompliant. Remove the stale final claim that nablarva's current buffer cannot
  qualify as-is when the dated facts explicitly say it had zero merges. These are wording
  consistency fixes; neither needs a new experiment.
