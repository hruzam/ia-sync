# CHALLENGE — preserve the operation, including after drop

**Weakest assumption:** a confirmed list of shell commands is sufficient to preserve the
relationship between selected Git content and live files through failure, retry and drop.
The narrative names partial states, but the executable-plan sketch does not maintain them.

**Verdict: REVISE before implementation GO.** Keep prefix selection, snapshot deployment,
the adapter boundary and the JSON interface. **Majkee's 2026-09-29 decision stands:** every
unpushed commit remains droppable, including `deployed_push_pending`; retain `pg-drop` and
its future button. I am not reopening eligibility. Define its effects and recovery truth.

**Primary risk:** publish/drop reports one clean deployed commit while the host contains
mixed, generated or orphaned bytes, and the only receipt identifying their origin has been
replaced or lost.

**One alternative:** retain the CLI but make each confirmed plan a small durable operation:
pinned inputs, mandatory checks, start receipt before effects, separate Git/deploy/push
outcomes, and an explicit recovery action. `pg-drop` changes history and requests redeployment;
it does not erase the prior deployment's identity or imply that additive copying undid it.

## Ranked findings and the smallest fold

### P1 — Snapshot purity cannot be a skippable proposal

§4 lines 172/186–188 allow declining the generator check. §7 lines 352–359 require it to
enforce the fixed committed-content rule. These are incompatible. The live script generates
`zsh/ai/temple-project-map.zsh` in write mode before copying zsh, and performs earlier deploy
legs before reaching that generator. A late or skipped check cannot protect those effects.

**Fold:** make preflight mandatory before the first live write; refuse on every nonzero
check result, not only exit 3. Resolve the adapter, check script and deploy script from the
pinned snapshot; retain their identities in the plan. A green check supports the present
deterministic generator, not arbitrary future build steps. Removing the check is a policy
change requiring a separate gavel, not an ordinary per-plan checkbox.

The receiving-host “local deploy.sh” shortcut (§1) and §7's offered dirty-tree hand-test
must not be described as compliant exceptions. The existing script may remain untouched,
but this gate's deployment path on either host uses the committed snapshot and mandatory
preflight. A missing local deployment receipt means **unknown**, not proof of not_deployed
on home (§5's sample).

### P2 — Implement the partial states in the plan, and carry them through `pg-drop`

The state list names `deploying` and failed legs, but §4 first writes state **after** a
successful `deploy.sh`. Kill the process after one rsync: files changed, yet the stamp
still describes an earlier deployment. A failed push may also have reached the server
before its acknowledgement was lost. Neither outcome is simply “did not happen.”

**Fold:** write an operation receipt before deployment, recording old target observations,
selected OID, host, actual destination set and expected remote ref. On restart, an unfinished
operation has unknown/partial effects until reconciled. Record deploy and push independently;
check remote state after an ambiguous push before retry. Existing deploy.sh emits human
output and can stop midway; don't promise exact per-leg completion evidence until the
adapter specifies how it obtains it. Unknown legs may remain unknown.

Apply the same sequence to **every drop that could affect live state**, including a commit
deployed through a descendant, partial deployment, or incomplete history of deployments:

1. Show the history change, new target derivation, affected destinations and residual-file
   inventory in the confirmed drop plan. Preserve the old OID/tree and receipt so later
   recovery does not depend solely on reflog retention or an unreachable Git object.
2. Perform the authorized history operation; record whether it completed. If rewriting
   descendants computes a new OID, bind the resulting target before its deployment rather
   than rereading a movable HEAD as though it were the original approved OID.
3. Deploy the new committed target with P1's checks. Failure means history may have changed
   while live files remain old/mixed. Keep that fact visible and offer recovery; do not
   rewrite it as either “drop failed, nothing happened” or a successful deployment.
4. Keep the residual list after redeploy. Additive copying leaves deleted/renamed outputs
   behind by design. Acknowledge them without automatic deletion or a false clean stamp.

The proposed source-tree `comm` difference is not an actual orphan inventory: source and
destination names differ (`zsh/config.office.zsh` → `~/.config/zsh/config.zsh`, Codex skills
→ `~/.agents/skills/`), and an incomplete deploy may not have installed every source file.
Let the adapter map source paths to physical destinations and distinguish observed leftovers
from candidates. Forward commits that delete files also create residuals; this is not only
a backward-move concern. Filename comparison must handle supported filenames losslessly.

### P3 — The core cannot inherit ia-sync's branch and linear-history assumptions

The worked ia-sync example correctly resolves to `main`/`origin/main` on this host. Nablarva
is `core`, and its flag L12 expressly forbids `pull --rebase` because of subtree history.
`rev-list --reverse` enumerates commits; it does not establish one linear chain. Merge
parents also make `<parent>` and a default revert ambiguous.

**Fold:** core resolves and pins the checkout, local branch, configured remote/target ref
and observed base. Project policy supplies integration behavior; ia-sync's rebase advice
does not become the core default. Define selection by ancestor closure, or explicitly
limit v0 to verified linear segments and report unsupported history. If the latter excludes
nablarva's actual history, do not claim that its inheritance is already solved. A merge
revert needs an explicit mainline choice; no guessed parent.

`pushed = ancestor of origin/main` also conflates a cached local observation with a current
publication fact. Before a destructive drop, establish publication status for the declared
publication scope, preserving known earlier successful publications. On stale/unavailable
evidence, report unknown and refresh/reconcile: “every unpushed commit is droppable” does
not classify an unknown or already-pushed commit as unpushed.

### P4 — Close the muticula client boundary in the actual commands

The r3 ownership direction is right: muticula owns claims, beacon and its commit gate;
publish-gate owns publication selection and receipts. **r3 has no general deploy-target
reservation API.** My September 25 resource-resolver memo is historical design advice,
not an API that exists in r3. Replace the obsolete RUNBOOK fixed fact and dangling §3.5.4
reference through the head's fold; don't grow those resources back to satisfy the old text.

Two concrete execution gaps remain:

- §2's `git revert <sha>` creates a commit directly, contradicting §7's requirement that
  enrolled commits go through `muticula commit`. A revised operation can prepare a revert
  without committing, then use the gate, but preparation itself changes index/worktree and
  needs explicit affected-path ownership, dirty-state preconditions and conflict/abort
  handling. `--no-commit` alone is not safe for a mixed index. Alternatively keep the whole
  operation human-coordinated, with the commit gate still honoured.
  [Git revert behavior](https://git-scm.com/docs/git-revert)
- There are more than two enrollment states. State present + missing/wrong/revoked key,
  damaged state, and a different checkout sharing the common dir must not fall into “plain
  Git otherwise.” Distinguish validated enrolled client, confirmed no muticula state,
  and refused/unknown authority. Missing `MUTICULA_ID` never proves a human. The new
  `pg-drop` entry needs the same explicit operator route and agent-deny treatment as its
  underlying human verbs; checking only whether ID is set leaves an unenrolled-agent hole.

The detached deployment worktree can read the common Git dir, but r3's claims do not govern
it. Do not enroll it implicitly or treat shared visibility as authority. Coordinate source
checkout operations through the valid client and keep snapshot materialization explicit.
Q5's proposed choice between registering/claiming and flock is a false substitute: a
read-only `--check` needs no source edit claim; a commit does; a deploy mutex grants neither.

### P5 — Lock the resource the adapter actually mutates

A common-dir flock serializes publish-gate calls sharing that Git store. A second independent
clone on the same host has another common dir and can deploy simultaneously into the same
`~/.config/zsh`, `~/.claude` or `~/.agents` destinations. Drop-triggered redeploy is also absent
from §3's stated “publish-to-here only” lock lifetime.

**Fold:** choose either one explicitly enforced deployment source per target, or a host-local
mutex keyed to the resolved physical target set that all this adapter's publish/redeploy
paths share. State the cooperative limit: direct deploy.sh calls bypass that mutex. It is
an adapter transaction mutex, not a second file-claim/beacon authority. A future muticula
deploy-resource provider replaces that responsibility through a deliberate handoff; r3 does
not supply it today. Keep any Git-operation serialization distinct and define acquisition
order; never hold a resource across operator deliberation.

### P6 — A confirmed plan needs input identity, not only command strings

§5's execute input is a list of command strings, while the required host/checkout/ref/base,
adapter digest, expected HEAD and prior deployment state are absent. The intended pre-execute
HEAD check in §1 is not in the actual step list. `/tmp/pg-<sha7>` is reusable and collision
prone. A confirmation can become stale before step 1 even with a fixed selected OID.

**Fold:** the plan carries an operation ID and the reviewed inputs above. Under the relevant
transaction mutex, revalidate them before effects, use an exclusively allocated snapshot
directory, and refuse stale plans. Treat the human-readable commands as the rendering of
those typed operations, not unrestricted shell text received from a dashboard. Define
resuming one interrupted operation separately from executing it twice.

The `ls-remote` check is useful, but another remote writer can move the ref after it. Normal
push provides a fast-forward constraint, not atomic equality with the earlier observed base.
Either narrow the contract to that behavior and reconcile the result, or specify a genuine
expected-old-value update **plus an independent no-history-rewrite check**. Adding force or
an unspecified lease is not the solution. Preserve the deployed receipt when remote movement
requires integration/replanning; never silently substitute a new tree.
[Git push constraints](https://git-scm.com/docs/git-push)
