## Curvature

### C1 — Bootstrap and caller/request scope (packet lines 52–64, 87–92, 148–151)

An absent database must return `store_unavailable`, but no explicit initialization operation
creates a valid fresh fixture. Auto-creating an empty database after accidental loss would
violate the stated rule. Add explicit create-only initialization and its existing/corrupt-store
outcomes; test simultaneous initialization and prove ordinary calls never recreate lost state.

`register` is idempotent, while its deduplication namespace requires the `actor_id` that register
has not returned yet. Define a pre-actor registration key. For later calls, identify the asserted
caller explicitly (an envelope/CLI context is sufficient), including release, cancel, handoff
and recover; scope replay and owner checks to it. This is internal consistency, not B2 identity
authentication. Make recover's release/transfer mode and target explicit; A18 expects transfer.

### C2 — Waiting/holding must be an invariant of every transition (lines 68–92)

Forbidding a held actor from joining the queue closes the original direction only. The reverse
is still open: an actor already waiting for A can request free B, or receive B by handoff/recover.
An actor with two tickets can also become a holder when one ticket grants while the other stays
live. Thus “a waiting actor never holds anything” does not follow from the listed preconditions.

Concrete transfer trace: H1 holds A and H2 holds B; X queues for A and Y queues for B; H1 hands A
to Y and H2 hands B to X. Neither handoff has a waiting-target prohibition. X now holds B while
waiting for A; Y holds A while waiting for B. This is a specification counterexample, not an
observed implementation failure.

Minimum cut: one immutable live ticket per actor; bind it to that actor and normalized bundle;
refuse unrelated acquisition and incoming handoff/recovery while it is live; consume the ticket
atomically with its grant. Cancellation then permits other acquisition. Held-actor expansion
must honor earlier overlapping tickets as well as physical freedom, and refuse without queuing.
Other policies are possible, but choose one and test every transition. Do not auto-cancel another
actor's ticket merely to make a transfer succeed.

### C3 — Completion input coverage and observation boundary (lines 88, 102–131)

- Acquire records bases per checkout, but check-completion accepts one candidate and one HEAD.
  Restrict each check to one checkout, or define an OID map. State empty/mixed/named-only scope
  outcomes; named inputs cannot be both syntactically forbidden and expected to reach predicate 7.
- Subtree enumeration omits the index. A new path can be staged and then deleted only from the
  worktree, leaving it absent from base, candidate and worktree but present in the index. The
  stated union never checks it and can return a false clean result. Include index paths and
  define comparison of entries/conflict stages. Git distinguishes index and worktree inventories;
  this counterexample follows from that model. [Git ls-files](https://git-scm.com/docs/git-ls-files)
- Reading a mutable index/worktree once, plus a timestamp, does not create a coherent snapshot.
  Example: read clean a; another writer dirties a and cleans b; read clean b. Both observations
  can appear clean even though the files were never simultaneously clean. Use immutable fixture
  observations or an explicit quiescent-input precondition for B1; any detected movement must
  yield uncertainty/failure. Do not imply that pre/post reads alone guarantee absence of races.
  B3 still owns live admission/drain and release revalidation.
- `base == candidate` makes the trailer-range predicates vacuous. Define whether this is an
  explicit no-change result or require a qualifying claim-marked commit for commit completion;
  never infer proof of the holder's commit from an empty range.

### C4 — Baselines for the resource types already admitted (lines 31–37, 94–98)

Creates and subtrees are legal, but the baseline is only “each granted existing file”. Specify
an absent-file marker and subtree membership snapshot, or explicitly restrict verify-baseline's
supported scope. Otherwise creating an absent target or adding a descendant has no defined
stale-base result. State what handoff/recovery does to baseline/base_oid for the new generation.
These are definitions/tests for existing operations, not additional features or runtime hooks.
