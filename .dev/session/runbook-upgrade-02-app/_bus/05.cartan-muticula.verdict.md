## Curvature

1. **Idempotent attempt versus a live ticket — packet lines 47–57, 65–70.** Returning an attempt's
   original `occupied` response is compatible with idempotency, but a later attempt must be able
   to become granted. Specify separate stable ticket and per-attempt request identities, actor/
   operation scoping, and rejection of the same request ID with a different payload. Spell out
   request semantics for register/cancel/recover too. Do not replay a stale grant as current
   authorization after release/recovery; adapters must validate the current generation.
2. **Atomic batches do not eliminate hold-and-wait — lines 67–73.** X can already hold A while
   queuing for B; Y can hold B while queuing for A. The blanket no-deadlock claim is false.
   Choose a bounded rule for additional acquisition and overlapping multi-resource tickets.
   Suggested small cut: no queued expansion while already holding resources; acquire the full
   needed bundle before work, or explicitly withdraw/replan. Define one enqueue order and which
   disjoint requests may proceed. Cancellation remains explicit; no hidden timeout takeover.
3. **Completion needs a complete, coherent predicate — lines 78–95.** The declared-done set is
   absent from the API/state schema. “Paths touched under the claim are within the claim” is
   tautological and does not reject extra unclaimed content. Define the exact completion scope,
   grant baseline/commit relation, tree comparisons, added/deleted/renamed/unchanged files,
   subtree handling, and merge/trailer ambiguity. A commit existing anywhere in a repo and a
   worktree clean against its current HEAD do not establish completion by that candidate.
   Concurrent claims/Git state need a stated snapshot or change-detection boundary. Read-only
   checking is a useful B1 limit; later release must revalidate and drain admitted operations.
   B2 identity alone does not make a caller-written trailer an authoritative completion receipt.
4. **Resource shape and tests disagree in several places — lines 29–43, 119–136.** Make file,
   subtree and named resources explicit types, including canonical aliases and unsupported
   cases. A4 cannot require the entire store unchanged while recording a conflict ticket;
   require unchanged grants plus the declared queue/request delta. A13 must test two-resource
   acquisition or a defined rename-plan check: a core with no write adapter cannot observe an
   arbitrary rename. A18's `--operator` is an explicitly cooperative assertion in B1, not proof
   of human approval. A newly created tracked-and-committed file can complete; distinguish it
   from non-Git external resources and files that remain untracked (lines 34 versus 91).
5. **Missing acceptance/scope details — §§6–7.** Add disjoint concurrent grants, denied retry
   after release, payload mismatch, overlapping ticket sets, the chosen hold-and-wait rule,
   stale-baseline detection, explicit release/handoff and idempotent mutation cases. Show the
   core works across unrelated fixture roots without a bed/dashboard and test named external
   resource contention. Give JSON result/error/exit semantics needed by black-box tests and an
   explicit fixture state-path override; no test may touch the live default XDG database.
   Broader B2/B4 runtime evidence remains deferred, not silently satisfied by core tests.
6. **Git resource mapping requires a boundary — packet §2 versus draft §3.5.4.** A checkout-index
   key does not cover shared refs across worktrees or nonstandard index paths. Either define
   their resolver now or explicitly limit B1 to opaque named keys and defer resolution to a
   client contract. The preliminary publish-gate input in
   `raw/cartan.publish-gate-boundary.2026-09-25.md` distinguishes reservation authority, executor
   ownership and publication recovery; it is not a second reservation implementation.

The packet's retention boundary is sound in intent, but “already-tracked matrix/verdicts” is
incorrect. A reviewed digest inventory records an observation and supports a later integrity
comparison; it neither stores the evidence nor guarantees its existence after cleanup. Raw
retention and any further commit remain separate decisions.
