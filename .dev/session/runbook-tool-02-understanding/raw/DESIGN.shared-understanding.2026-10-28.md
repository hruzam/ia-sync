## Options

| Shape | Benefit | Cost / failure | Decision |
|---|---|---|---|
| Existing RUNBOOK, bounded STATUS, exact evidence pointers | Least maintenance; preserves authority | Entrant may still need several reads | Baseline recommendation |
| Living shared understanding file | Useful synthesized disagreements and rationale | Dedicated editor, stale prose, duplicated authority | Optional only after repeated retrieval need is shown |
| Derived index/view | Reuse, dependency/change visibility | Parser/invalidation work; semantic completeness cannot be inferred | Defer build; current TUI is already a limited view |

An optional entry note recommends a starting slice and permits reading further. It names
assignment, current authoritative source and relevant evidence; it does not copy live
holds/next or authorize execution. Revision/hash means changed bytes, not truth or approval.

The challenger correctly rejected an earlier formulation that left procedure changes
without a durable address. Revised proposal: each effective procedure change has one
attributed decision artifact, explicit scope, effective revision, superseded revision,
affected assignments, and approval source. STATUS points to it and carries only current
consequences. Assignments name their base. This is a proposed practice, not a new schema
or canon. During the session its exact evidence path is retained; before pruning, the
owner promotes it to the project's approved evidence home and updates consumers. Missing
destination or missing approval means unresolved, never effective by inference.

## Bounded worked example

All names/revisions below are hypothetical. No artifacts were dispatched, no procedure
approved, and no running work changed. The same design gate remains in force.

1. Entrant E is assigned to compare two entry formats. It reads RUNBOOK and current
   STATUS, follows the pointer to decision D1 (procedure P1), and records assignment A
   against P1. It may inspect original evidence or challenge D1. Expected action: compare
   formats, with no implementation or dispatch authority.
2. Owner proposes P2: compare correctness of the next action before comparing reading
   length. The authorized decision owner accepts this method change in D2, which names
   P1, A and its effective scope. Acceptance criteria and permissions are unchanged.
   STATUS points to D2; A is flagged for reconciliation. If acceptance changed instead,
   open a sibling under existing law. This example does not authorize D2 in this session.
3. Owner sends the exact D2 pointer to the affected active participant through an authorized
   channel. Sending is not reading: E must identify P2 and its consequence on its next
   return. If E cannot be reached, work remains unreconciled; do not infer uptake.
4. Fork F returns its P1-based comparison after D2. Owner retains its measured reading
   lengths as evidence, identifies the missing correctness comparison, and requests only
   that delta against P2. Old evidence is not discarded merely for age. A BUS exchange,
   when applicable, uses a new corrective cycle rather than editing handed-off receipts.
5. A newcomer after D2 follows STATUS to the effective decision without replaying D1's
   whole history. Conflicting pointers or absent approval stop dependent action and prompt
   owner reconciliation. An optional summary cannot resolve that conflict by assertion.

| Adverse input | Safe resolution in the example |
|---|---|
| STATUS still points to P1 but D2 appears | Check D2 authority, scope and effective revision; owner repairs snapshot; no automatic execution |
| Partial RETURN | Mark incomplete/unverified; request missing receipt content or evidence only; resume execution only after the recovery probe establishes the safe edge |
| RETURN changes after handoff | Preserve reviewed version or mark unverifiable; correction in new cycle; no silent acceptance |
| Wrong seat/cycle/base binding | Quarantine claim pending binding check; filenames do not prove identity |
| Unknown execution | Read-only runtime/side-effect probe; if inconclusive keep uncertainty, do not redispatch |
| Late return to closed cycle | Assess information in a new cycle; do not reopen or replace old verdict |
| Duplicate dispatch request | Check declared assignment and execution state; uncertain prior run blocks a second side effect |

Demonstrated: a logically explicit entry/change/reconciliation path and disposition for
all seven named cases. Not demonstrated: real delivery, reader uptake, fresh cold recovery,
concurrent publication safety, identity attestation, reduction in reading time or tokens.
