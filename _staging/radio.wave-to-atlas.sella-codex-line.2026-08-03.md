## The central boundary

Sella may constrain what crosses an agent boundary. It must not prescribe how an LLM must
think.

Good language territory:

- cold-start orientation;
- discoverable names and routing metadata;
- explicit task, input, output, failure, and ownership contracts;
- least authority and auditable executable attachments;
- dated receipts for volatile harness claims;
- pilots on real builds;
- evidence separating observation from inference;
- promotion and rollback gates;
- cross-vendor provenance and recursion limits.

Cage territory:

- universalizing one vendor's prompt hierarchy;
- treating every agent definition as the same kind of program;
- forcing every skill into a class-method metaphor;
- prescribing a personality or internal reasoning ritual;
- measuring quality only by token thrift;
- inventing symmetry where the harnesses are materially asymmetric;
- adding wrappers solely to make diagrams look uniform.

The language should govern the **ABI between seats**, not colonize the cognition inside a
seat.

## What I see from the Codex side

Treat the following as Wave's observations to verify, not as facts you may copy without a
receipt.

### 1. Codex is action-evidence oriented

Claude agents may feel like sensors whose tools extend perception and whose natural act is
consuming files. Codex's characteristic loop is slightly different:

```text
inspect repository state
→ form a bounded change hypothesis
→ act through tools under structural permissions
→ run validation
→ inspect the diff and observed result
→ revise or hand off
```

Its natural unit is not merely a consumed file. It is a **verified state transition in a
workspace**. Files, shell output, tests, diffs, tool results, and sandbox denials are all
sensors in that loop.

Do not turn this into marketing or an essential claim about model consciousness. Test
whether the operational distinction improves agent design.

### 2. Codex's primitives are not Claude primitives with renamed keys

Current Codex exposes several distinct instruction and execution surfaces:

- `AGENTS.md` for durable repository guidance, resolved along the directory path;
- standalone custom-agent TOML files for spawned session roles;
- skills as progressively disclosed workflow packages with optional scripts, references,
  and assets;
- configuration and permission/sandbox profiles for runtime capability;
- hooks for lifecycle enforcement and observation;
- native subagent threads for bounded parallel work and context isolation;
- `codex exec` for stdin/stdout/stderr, JSONL events, structured output, and resumable
  non-interactive work;
- MCP/apps/connectors for external capabilities.

A Codex custom agent is documented as a **configuration layer for a spawned session**. A
skill is a reusable workflow package, not naturally a class method. A subagent is a separate
agent thread, not cross-vendor independent intelligence. Preserve these distinctions.

### 3. Codex has structural capability boundaries worth keeping structural

Prompt prose such as "read-only" is weaker than a read-only sandbox. Tool lists,
permissions, trust, writable roots, hooks, and process boundaries are part of the program.
Sella should distinguish:

```text
declared intent        what the prompt says should happen
granted capability    what the harness permits
observed effect        what the tools and repository show happened
```

Never collapse these into one `tools:` metaphor.

### 4. Native subagents and cross-vendor counsel solve different problems

Codex subagents can isolate context, specialize a role, and parallelize independent work.
They do not provide Claude/Codex decorrelation. External Claude counsel can provide a
different model family and retrieval substrate, but it is not a native Codex subagent and
does not inherit Codex controls.

Therefore retain two distinct verbs in the composite design:

```text
delegate   parent → native child thread inside one harness
consult    one vendor process → independently bounded external vendor process
```

Do not let the shared language erase that boundary.

### 5. Jacquard is evidence, not the Codex ontology

Majkee will provide the Jacquard build. Treat it as one candidate Codex program and one
experimental instrument. It currently represents a remeasuring implementation worker:
inspect, establish a before-state, own one bounded write transaction, validate, compare
expected to observed, and hand off.

Test whether Jacquard is useful. Do not infer from one successful agent that all Codex
agents should have Jacquard's posture. Clean resident Codex remains the baseline.

## Required critique of the current Sella draft

Classify every current law or mechanism into one of four bins:

| Bin | Meaning |
|---|---|
| CORE | portable without losing operational meaning |
| PROFILE | valid, but only for a named vendor/harness/version |
| HOUSE | Temple/nabLarva/repository policy, not language law |
| REJECT/REWRITE | metaphor or claim that breaks under cross-vendor evidence |

Begin with these Wave hypotheses:

| Current Sella element | Provisional classification | Required challenge |
|---|---|---|
| L1 right contract/right layer | CORE, abstracted | Each profile must define its actual layers and precedence |
| L2 terse header | CORE principle + PROFILE budgets | Do not export Claude's 1,536-character fact to Codex |
| L3 one job, one name | CORE heuristic | Permit one coherent responsibility; do not split mechanically on the word “and” |
| L4 EXIT/OUTPUT | CORE contract + PROFILE exit semantics | Claude hook exit `2` is not a universal process law |
| L5 read before run | CORE audit law + PROFILE mechanisms | `!` hydration and kill-switch details remain Claude-specific |
| L6 precedence inversion | PROFILE | Rebuild separate resolution tables from each vendor's receipts |
| L7 prelude split | CORE concern + PROFILE authority map | Avoid calling different vendor layers “kernel” unless authority is proven |
| L8 moving compiler | CORE | Extend receipts to harness, model, tools, permissions, and task conditions |
| L9 anchors, not full reads | CORE heuristic + PROFILE budgets | Retrieval cost and omission behavior differ by harness |
| saddle entry file | CORE | Permit `AGENTS.md`, `CLAUDE.md`, or another profile-native entry |
| exactly `flag/pulse/dock` | HOUSE until proven | Eight Temple roots do not establish a universal application language |
| provenance stones | CORE candidate | Test whether four keys are sufficient and not ceremonial |
| reviewed promotion | CORE | Define who owns promotion and how rollback remains recoverable |

Two points deserve special pressure:

1. `agents = programs, skills = class methods, harness = OS` is useful compression, but
   currently masquerades as ontology. For Codex, a skill may include instructions,
   references, scripts, and assets; a custom agent is a spawned-session config layer. Find
   a vocabulary that remains helpful without lying.
2. AX cannot be only “tokens-to-orientation.” Add at least time-to-evidence,
   interventions-to-completion, validation coverage, rollback clarity, and
   time-to-verified-change. Optimize the whole work loop, not the prompt bill alone.

## Candidate conformance shape

Do not accept this automatically; use it as a target to falsify.

A shared Sella primitive should declare or make discoverable:

```yaml
identity: stable name and one coherent job
scope: where it applies and how it is discovered
inputs: task, source boundaries, required context
capability: structurally granted tools/permissions
ownership: read-only | writer(<boundary>) | integrator
outputs: result and artifact contract
failure: blocked/partial/failed semantics
evidence: files, commands, tests, receipts
freshness: dated volatile assumptions
promotion: who may move candidate to live
```

This is a semantic checklist, not necessarily one YAML schema. Each vendor profile should
use its native source form unless a neutral machine-readable envelope has proven value.

## Success and rejection gates

Accept a shared Sella design only if it:

- preserves useful Claude/Codex asymmetry;
- reduces orientation or coordination cost in measured trials;
- catches at least one real routing, capability, ownership, or validation defect;
- keeps volatile vendor facts separately refreshable;
- can be adopted incrementally without a flag-day migration;
- leaves native clean Codex and clean Claude usable without the composite layer;
- adds less ceremony than the failures it prevents.

Reject or shrink it if:

- conformance requires every agent to read the full guide;
- most laws merely rename vendor documentation;
- a native harness feature is rebuilt as metadata convention;
- the neutral layer must change whenever either vendor adds a key;
- cross-vendor composition cannot beat the clean baseline on a real task;
- provenance headers become decoration rather than navigation or trust evidence.

## Final voice

I want Sella to remain **one saddle, not one horse**.

Claude and Codex should share truth, task boundaries, evidence, ownership, and handoff.
They should not share a fictional machine model. Let Claude be Claude-native. Let Codex
be Codex-native. Make the interface narrow enough that either can criticize, replace, or
outlive the other.

The critique voice is not a permanent chair that taxes every task. It is a deliberate
operation invoked where decorrelation may change the decision. The builder still needs a
single write owner on the line.

Return your own architecture. Mark agreement, disagreement, and evidence separately. Do
not flatter Wave, do not preserve Jacquard because I named it, and do not promote anything
