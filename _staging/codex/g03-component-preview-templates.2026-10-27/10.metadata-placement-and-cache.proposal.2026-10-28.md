## Direct answers

Frontmatter is one convenient parser boundary, not a requirement. Deterministic extraction
needs a declared format, unambiguous boundaries and stable field meanings. A reserved
structured section, explicit backmatter block or declared sidecar can also work. Ordinary
headings need rules for duplicates and literal examples; fixed line numbers are fragile.

Metadata already on disk consumes no model context merely by existing. A local mechanism
can parse the complete header and return only a small preview. Moving fields out of the
header does not itself save context. The returned text determines intake.

A physical derived cache is possible. It can save repeated extraction and projection.
It supplies no model memory or proof that the current agent consumed an instruction body.

## Recommended starting arrangement

1. Keep the five-field thin B core first: schema, id, kind, name, short description.
   Natural prefix reads then remain useful when no projector or cache is available.
2. Keep operational instructions in the complete contract body.
3. Add at most one explicitly bounded optional metadata section when needed. Small metadata
   can remain in the header; substantial, rarely selected metadata can use backmatter.
4. A mechanism may derive a local preview cache and return only the requested collection.

Illustrative backmatter boundaries, not an adopted parser grammar:

```text
<!-- germline-meta:begin -->
[one versioned structured metadata block]
<!-- germline-meta:end -->
```

Before implementation, define the block grammar, duplicate/malformed-block handling and how
literal examples are distinguished from actual metadata. The mechanism must find the core
and boundary without first reading optional read_hints.

Metadata may refer to an explicit body section to preserve one authored home for a fact.
An extracted excerpt retains its origin; it is not silently presented as an authored
description or a complete behavioral contract. Required behavior must remain available in
the selected complete contract, rather than being hidden in an omitted preview-only field.

| Placement | Useful when | Cost |
|---|---|---|
| Compact frontmatter | Information routinely helps selection and manual first reads | Longer headers increase prefix output |
| Structured backmatter | Rich metadata is infrequent and one-file ownership matters | Needs bounded extraction to omit it; full cat still returns it |
| Authored sidecar | Metadata is large, independently maintained, or the contract file must stay lean under cat | Linkage, relocation and consistency machinery; two-source provenance |
| Derived cache | Repeated extraction/projection is worth avoiding | Invalidation and cache-version bookkeeping |

A manually authored sidecar is a source. A generated cache is replaceable derived data.
They have different authority and maintenance roles.

My lean is a single-source default with a bounded extension; introduce authored sidecars
only when a concrete consumer needs them. For sidecars, either keep separate linked records
or declare a composite record with every contributing revision and per-field origins.

## Physical cache proposal

A host-local directory, for example `~/.cache/germline-preview/`, would suffice.
This path is illustrative; no cache directory or mechanism was created.
Keep derived cache data outside portable germline source and outside the model's routine
startup intake. No daemon is required.

An entry's identity needs all inputs that affect its result:

```yaml
cache_schema: germline-preview-cache/draft-01
inputs:
  sources:
    - root: caller-selected-source-root
      relative_path: functions/reconcile.md
      sha256: "<hash of captured source bytes>"
  parser_version: "<extractor revision>"
  adapter_version: "<adapter revision or explicit not-applicable>"
  record_schema: germline-preview/draft-02
  projection:
    collection_definitions_sha256: "<exact collection definitions>"
    output_options_sha256: "<relevant limits and formatting options>"
payload:
  record: "<normalized metadata and provenance>"
  projection: "<requested preview, where cached>"
```

- Parse and hash the same captured bytes. Include every source contributing to a composite
  record. Recheck the source revision when connecting a preview to a later body read.
- Size/mtime can accelerate invalidation but are not content identity. Correct content
  hashing may still read the whole file; do not claim guaranteed I/O savings.
- Publish complete cache entries atomically. Reject corrupt or incompatible entries.
  Label deliberately stale output; missing data remains a diagnostic, not fabricated success.
- Apply the calling task's source/read boundaries to cached material as well as direct reads.
- Cache stays derived and replaceable. Its presence does not select a card, grant a write,
  prove body delivery, or prove that a fresh/recovered model context retains prior content.

The mechanism can keep detailed cached data machine-side and return only a requested
catalog/select/inspect result. Detailed instruction bodies and dependency reads remain
separately selected under the actual loader. Reading an index into context every turn
would defeat that selective-output purpose.

Native discovery has its own format rules. This proposal does not establish that a vendor
will automatically discover our backmatter, sidecars or cached records.

## Decision edge and evidence needed

The open format choice is single-source extensions versus deliberate composite sidecars.
Choose the single-source default for a first consumer, then measure whether cache complexity
is justified. Capture preview size, unnecessary full reads, freshness detection and complete
selected-body delivery separately. Tokens, cost and retained understanding stay unknown
unless actually observed.

No parser, cache, native integration or performance result is released by this document.

INSIGHT: Metadata placement, extraction, physical caching and model context intake are separate design choices.

RECOMMENDATION: Keep the five-field B core first. Use one explicitly bounded optional metadata section as the initial extension mechanism. Add an optional local projector and derived cache only when a consumer needs them.

Frontmatter is **not necessary** for deterministic parsing. The parser needs an unambiguous grammar: frontmatter delimiters, a reserved section containing structured data, a delimited backmatter block, or a declared sidecar format can all work. Stable headings help navigation, but ordinary headings alone need rules for duplicates and examples. Fixed line numbers are fragile. Arbitrary prose requires interpretation rather than reliable field extraction.

The latest [reading proposal](/home/hruzam/ia-sync/_staging/codex/g03-component-preview-templates.2026-10-27/09.read-recommendations.proposal.2026-10-28.md) correctly distinguishes a prefix from a validated projection. Its read hints should remain optional: readers must already know how to find the core and extension boundary without first consuming the hints.

**Placement tradeoffs**

- **Optional header fields** suit small extensions routinely useful during selection. They retain one-file coherence but lengthen natural prefix reads.
- **Backmatter** suits substantial, infrequently needed metadata while preserving one-file ownership. It keeps the opening compact, but `cat` still returns everything. A bounded extraction operation is needed to omit it.
- **Sidecars** win when metadata is large, maintained independently, or generated, and ordinary `cat` of the contract should stay lean. They introduce linkage, relocation and consistency costs.

Sidecars also change the existing “one exact source file per record” rule. Either return separate linked records or declare an explicit composite record with both source revisions and per-field origins. Do not silently present a two-file result as one-source evidence. Each field needs one authoritative authored location.

Thus, moving metadata outside the header does not by itself save context. Savings come from bounded model-facing output—including diagnostics and excerpts. A parser can inspect substantial local data without returning it all. Native discovery must not be assumed to understand our extensions, backmatter or sidecars.

**Physical cache: feasible, optional, derived**

A host-local directory of cache files is sufficient; no daemon is needed. Minimum rules:

1. Key extracted records by hashes of every contributing source, parser/adapter version and normalization schema. Key projections additionally by collection definitions and relevant output options.
2. Hash and parse the same captured bytes. Preserve their origins. Recheck the selected source before claiming a subsequent body read matches the preview.
3. Treat size/mtime as acceleration hints, not content identity. They can miss changes. Content hashing may still require reading the entire file, so caching does not guarantee reduced I/O.
4. Publish cache entries atomically. Reject incompatible or corrupt entries. Label deliberately stale results; never silently report them as current.
5. Cache content remains replaceable derived data. It grants no authority and proves neither body delivery nor retained model context. It creates no requirement to reread instructions every turn.

Caching principally saves extraction and projection work; selective output saves context.

CURVATURE: The main downside is extra consistency machinery for potentially tiny files. Neither this arrangement nor native integration or savings has been implemented or measured here.
